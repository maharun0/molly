# Molly — Project Notes for Claude

A from-scratch C++20 game engine (Windows only) with an ImGui-based visual editor, built as a CSE499A capstone project. See `plan/PLAN.md` for the original 10-milestone build plan, `plan/EDITOR_UI_PLAN.md` for the editor UI overhaul, `plan/GAPS_AUDIT.md` for a current what-exists-vs-what's-missing audit, and `reports/CSE499A_Report.tex` for the formal writeup.

## Build

Everything is vendored under `vendor/` as git submodules — no vcpkg/Conan, no external package manager. This is a deliberate, explicit project requirement; don't introduce one.

```
cmake --preset windows-debug
cmake --build build/windows-debug --config Debug --target molly-editor molly-demo molly-tests -j
```

Targets: `molly-engine` (static lib), `molly-editor`, `molly-demo`, `molly-tests` (Catch2).

Run:
```
.\build\windows-debug\bin\editor\Debug\molly-editor.exe
.\build\windows-debug\bin\game\Debug\molly-demo.exe
.\build\windows-debug\tests\Debug\molly-tests.exe
```

All three chdir to their own executable directory at startup (`molly::setWorkingDirectoryToExecutable()`, called first thing in `main()`), and CMake `POST_BUILD` steps copy each target's `assets/` next to its exe — so they're launchable from anywhere (double-click, VS debugger, any terminal cwd), not just from a terminal `cd`'d into `editor/`/`game/`.

**Before rebuilding editor/demo**: kill any running instance first (`taskkill /F /IM molly-editor.exe` etc.) — the linker fails (`LNK1168`) if the exe is still running.

## Architecture

- `engine/` — `molly-engine`, static lib. All reusable subsystems: core/Application/Window/Layer stack, renderer (OpenGL 4.6, forward + Blinn-Phong), ECS (`entt`), physics (Jolt), scripting (Lua/sol2), resource manager (hot-reload), audio (miniaudio), scene serialization (nlohmann/json).
- `editor/` — `molly-editor`. Links the engine, adds editor-only panels (Hierarchy, Inspector, Viewport, Content Browser, Console) and the docking layout.
- `game/` — `molly-demo`. A hand-written sample game linking the engine the same way a third-party consumer would — this is *not* generated by the editor; there's no Build/Export pipeline yet (see gaps audit).
- `tests/` — Catch2 suite. Currently covers scene/prefab **serialization round-trips only** (transform, light, rigid body/collider, character controller, script, camera, hierarchy) — not rendering output, physics accuracy, or editor UI.
- `vendor/` — GLFW, GLAD, GLM, entt, Jolt Physics, Lua+sol2, Dear ImGui (docking branch), Assimp, stb_image, miniaudio, spdlog, nlohmann/json, Catch2.

Both `molly-editor` and `molly-demo` share `RenderSystem::renderScene()` (`engine/src/ecs/Systems/RenderSystem.cpp`) as the single render entry point — fixes there apply to both.

## Known gotchas (already fixed, but worth knowing why)

- **entt iterates in reverse creation order.** Don't assume draw/processing order matches creation order.
- **Depth testing must stay enabled** (`RenderSystem::renderScene`) — it was missing once already and caused later-created-but-behind objects to render on top of nearer ones.
- **Mouse wheel / ImGui input timing**: `io.MouseWheel` (and other ImGui per-frame input state) is only fresh *after* `ImGui::NewFrame()`. The app loop runs `onUpdate()` for all layers *before* `ImGuiLayer::begin()` (`Application::renderFrame`) — so read ImGui input state in `onImGuiRender()`, not `onUpdate()`, or you'll read a stale value.
- **Jolt's `Factory::sInstance` is process-global**, not per-`PhysicsWorld` — reference-counted init/shutdown handles this already; don't naively re-init per instance.
- **entt zero-storage optimization**: a truly empty component struct (`std::is_empty_v<T>`) makes `registry.get<T>()` return `void`, not `T&`. Components need a dummy field if they're used generically.
- **Never destroy an entity while iterating a `registry.view<...>()` over it** — defer to after the loop.
- **`molly-editor`'s `MainCamera` entity has two positions**: the `TransformComponent.position` and the `CameraComponent.camera`'s own internal `PerspectiveCamera` position are *not* automatically synced by any system — set both explicitly if you move the default camera.

## Conventions from this session

- Only commit when explicitly asked. Never commit with `git add -A`/`.` blindly — check `git status` first, there are usually stray test-run artifacts (`imgui.ini`, `*.scene.json`, `*.prefab.json` under `game/assets/prefabs/` or repo root) that shouldn't be staged.
- Commit messages: no `Co-Authored-By` trailer unless the user hasn't said otherwise — this has been explicitly requested for several recent commits. When in doubt, ask.
- After any editor/engine change, verify with: a clean build, a short headless run checking the log for errors, and (for editor UI changes) inspecting the auto-generated `imgui.ini`'s `[Docking][Data]` section to confirm dock-node structure — this project has no way to screenshot/see the rendered UI directly, so structural/log verification is the substitute.
- The report (`reports/CSE499A_Report.tex`) is IEEE `conference`-class two-column, matching the department's own sample template. Verify LaTeX structural correctness manually after edits (brace balance, `\label`/`\ref` pairs, `\cite`/`\bibitem` pairs) — no LaTeX distribution is installed in this environment to compile against.
